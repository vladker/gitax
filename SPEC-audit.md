# Feature: Аудит канала MAX (audit_channel)

## Цель
Проверка целостности публикаций репозиториев в канале MAX:
каждая публикация должна содержать описание (about) + полный набор файлов.
Если файлов не хватает — удалить битую публикацию и перевыложить
по стандартному механизму.

## Термины
- **Публикация** — набор сообщений в канале MAX, состоящий из:
  - 1 сообщение с описанием репозитория (📦, 🔖 версия, 🔗 GitHub)
  - 1+ сообщений с файлами (.zip или .7z.001, .7z.002, ...)
- **Битая публикация** — описание есть, но файлов нет / не хватает томов
- **Журнал** — `journal.json`, содержит записи со статусами `sent` / `failed`

## Требования

### 1. Сканирование ленты (`scan_all_messages`)
1.1 Подключиться к MAX через CDP (Playwright)
1.2 Найти контейнер чата (`[class*="scrollable"]`)
1.3 Циклически скроллить вверх (`scrollTop -= 500`, пауза 800ms)
     до полной загрузки всех сообщений
1.4 Критерий остановки: 3 итерации без прироста кол-ва сообщений
1.5 Из каждого сообщения извлечь:
    - Текст, HTML
    - Признак описания репозитория (📦)
    - Признак файла (.zip, .7z, размер MB/GB, скачать/download)
    - display_name, version, full_name (из 🔖 и 🔗 строк)
    - Имена файлов

### 2. Группировка публикаций
2.1 Сообщение с 📦 = начало новой публикации
2.2 Все последующие file-сообщения до следующей 📦 = файлы этой публикации
2.3 Результат: список групп `{desc, files[], repo_name, version, full_name}`

### 3. Матчинг с журналом
3.1 Ключ матчинга: `(full_name, version)` — уникальная пара
3.2 Если в журнале нет записи с такой парой — публикация не наша
     (возможно старая версия), пропускаем
3.3 Если в журнале есть `(full_name, version)` со статусом `sent` или `failed`
     — проверяем целостность

### 4. Определение проблем
4.1 **NO_FILES** — описание есть, файловых сообщений нет
4.2 **MISSING_VOLUMES** — есть тома `.7z.001, .7z.003`, но нет `.7z.002`
     (разрыв последовательности)
4.3 **NOT_IN_CHANNEL** — в журнале статус `sent`, но публикация
     с такой `(full_name, version)` не найдена в ленте
4.4 **FAILED_NO_FILES** — в журнале `failed`, в ленте нет файлов

### 5. Вывод результатов
5.1 Показать таблицу проблемных публикаций:
     `# | full_name | version | проблема`
5.2 Если проблема не найдена: `"✓ Все публикации целостны"`

### 6. Интерактивное восстановление
6.1 Для каждой проблемной публикации показать:
     - full_name, version
     - описание проблемы (чего не хватает)
6.2 Варианты действий:
     - `[Enter]` — исправить эту (удалить битое + перевыложить)
     - `[S]` — пропустить
     - `[A]` — исправить все без дальнейших запросов
6.3 **Исправление одной публикации:**
     6.3.1 Удалить все её сообщения из канала (сначала файлы, потом описание)
            через контекстное меню (правая кнопка → "Delete")
     6.3.2 Скачать свежий ZIP с GitHub
     6.3.3 Отправить через стандартный `send_message_with_files()`
     6.3.4 Обновить запись в журнале
6.4 Пауза между исправлениями: `repo_delay` из конфига

### 7. Удаление сообщений (`delete_message_by_index`)
7.1 Клик правой кнопкой мыши по элементу сообщения
7.2 Ожидание появления контекстного меню (500ms)
7.3 Клик по последнему пункту меню "Delete"
7.4 Ожидание исчезновения сообщения (1000ms)
7.5 Вернуть True/False

### 8. Интеграция в меню
8.1 Добавить пункт `[5] Аудит канала` в главное меню
8.2 После завершения — возврат в меню

### 9. Обработка ошибок
9.1 Если подключение к MAX не удалось — сообщить и вернуться в меню
9.2 Если удаление сообщения не сработало —
     пропустить публикацию и продолжить со следующей
9.3 Если перезаливка не удалась — обновить статус в журнале на `failed`

### 10. Критерии приёмки
10.1 Программа находит битые публикации (описание без файлов)
10.2 Программа находит пропущенные тома (.001 есть, .002 нет)
10.3 Программа находит публикации из журнала, отсутствующие в канале
10.4 Программа удаляет битую публикацию и перевыкладывает
10.5 Режим "A" исправляет все без запроса
10.6 Версия репозитория учитывается при матчинге
