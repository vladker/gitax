## Problem Statement

Нужна функция для выкладки фотографий и видео из указанной папки в отдельный MAX канал.
Файлы отправляются **без сжатия и без дробления** — как есть.
Программа убеждается что каждый файл успешно загружен перед переходом к следующему.
Уже загруженные файлы не отправляются повторно.

## Constraints

- Файлы отправляются **по одному** — отдельное сообщение на каждый файл
- Файлы **остаются на месте** после загрузки (не удаляются, не перемещаются)
- **Один запуск** — не бесконечный мониторинг
- Журнал ведётся по **имени файла + размеру** (не хеш содержимого — слишком дорого для видео)
- Файлы **сортируются по дате создания** перед отправкой
- Отдельный MAX канал указывается через `MEDIA_CHANNEL_URL` в `.env`
- Сжатие и дробление (7z split) **отключены** полностью

## Approach

**Новый модуль `media_archiver.py`** — самостоятельный скрипт, отдельный от `github_archiver.py`.

**Почему отдельный модуль, а не фича внутри архивера:**
- Разная логика: архивер работает с GitHub API → скачивает → отправляет. Медиа-архивер работает с локальной папкой.
- Разный канал: медиа идут в другой канал.
- Разный журнал: критерии "уже отправлено" другие (имя + размер вместо repo + версия).
- Минимальный риск: изменения не затрагивают существующий архивер.

**Что переиспользуем:**
- `BrowserMAX` — вся браузерная автоматизация, CDP подключение, загрузка файлов, подтверждение.
- `logging_config.py` — логирование.
- Метод `send_message_with_files()` — уже умеет загружать файлы и подтверждать.

## Architecture

### Компоненты

```
media_archiver.py          # Новый модуль — точка входа
media_journal.json         # Новый журнал (JSON, в папке проекта)
.env                       # Добавляется MEDIA_CHANNEL_URL, MEDIA_WATCH_DIR
config.yaml                # Добавляется секция media_archiver
```

### Поток работы

```
Запуск media_archiver.py
  ├─ load_dotenv() + загрузка config.yaml
  ├─ проверка MEDIA_CHANNEL_URL и MEDIA_WATCH_DIR
  ├─ загрузка media_journal.json (список уже отправленных: имя + размер)
  ├─ подключение браузера (BrowserMAX, CDP к Chrome:9222)
  ├─ навигация к MEDIA_CHANNEL_URL
  ├─ сканирование папки MEDIA_WATCH_DIR
  │    ├─ фильтрация по расширениям (фото + видео)
  │    └─ сортировка по дате создания (ascending)
  ├─ для каждого файла (по одному):
  │    ├─ проверка в журнале (имя + размер)
  │    ├─ если уже отправлен → пропуск
  │    ├─ browser.send_message_with_files(
  │    │     text="",
  │    │     filepaths=[filepath],
  │    │     split_threshold_mb=999999   # отключает дробление
  │    │   )
  │    ├─ ожидание подтверждения загрузки
  │    ├─ запись в журнал (имя + размер + время)
  │    └─ логирование результата
  ├─ сохранение журнала
  └─ завершение
```

### Журнал медиа (`media_journal.json`)

**Формат:**
```json
{
  "entries": [
    {
      "filename": "photo_20260601.jpg",
      "size_bytes": 4829312,
      "sent_at": "2026-06-08T14:32:00",
      "status": "sent"
    },
    {
      "filename": "video_clip.mp4",
      "size_bytes": 52428800,
      "sent_at": "2026-06-08T14:35:00",
      "status": "sent"
    }
  ]
}
```

**Ключ дедупликации:** `filename + size_bytes` — если файл с таким именем и размером уже в журнале, он пропускается.

**Почему не хеш содержимого:** Вычисление MD5/SHA256 для видеофайлов по 1-2 ГБ занимает минуты. Имя + размер — достаточно для нашей задачи.

**Атомичность записи:** Как в `journal.py` — запись во временный файл + `os.replace()`.

## Configuration

### `.env` (добавляется)

```env
MEDIA_CHANNEL_URL=https://web.max.ru/...
MEDIA_WATCH_DIR=C:/path/to/media/folder
```

### `config.yaml` (добавляется секция)

```yaml
media_archiver:
  watch_dir: null              # путь к папке (если null — берётся из MEDIA_WATCH_DIR)
  extensions:
    images: [.jpg, .jpeg, .png, .gif, .webp, .bmp, .tiff]
    videos: [.mp4, .mov, .avi, .mkv, .webm]
  retries: 3                   # повторные попытки на файл
  retry_delay: 10              # задержка между попытками (сек)
```

## Data Flow

1. **Сканирование:** `os.walk()` по `MEDIA_WATCH_DIR` → фильтрация по расширению → список файлов.
2. **Сортировка:** `os.path.getctime()` (дата создания) → ascending order.
3. **Дедупликация:** для каждого файла → `(filename, size)` в журнале? → да = пропустить.
4. **Загрузка:** `BrowserMAX.send_message_with_files()` → один файл → подтверждение → журнал.
5. **Порядок:** последовательный, не параллельный. Каждый файл ждёт подтверждения предыдущего.

## Error Handling

| Ситуация | Стратегия |
|----------|-----------|
| Файл не загрузился после `retries` попыток | Записать в журнал как `failed`, логировать, перейти к следующему |
| Браузер отключился | `BrowserMAX` reconnect (существующая логика), продолжить с текущего файла |
| Файл заблокирован другой программой | Логировать ошибку, пропустить, записать как `failed` |
| Папка недоступна | Логировать, завершить с ошибкой |
| `MEDIA_CHANNEL_URL` не указан | Логировать, завершить |
| `MEDIA_WATCH_DIR` не найдена | Логировать, завершить |
| Файл нулевого размера | Пропустить с логированием |

## Testing Strategy

1. **Юнит-тесты для журнала:** запись/чтение, дедупликация по имени+размеру, восстановление после сбоя.
2. **Юнит-тесты для сканирования:** фильтрация по расширениям, сортировка по дате создания.
3. **Моки для BrowserMAX:** тест полного потока без реального браузера.
