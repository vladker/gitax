# Backuper — Резервное хранение папок в канале MAX

**Дата:** 2026-06-10
**Статус:** implemented

---

## Problem Statement

У нас есть архиваторы для GitHub репозиториев и PyPI пакетов, но нет общей функции для резервного хранения **любой пользовательской папки** в канале MAX. Существующий `channel_downloader.py` скачивает файлы из канала, но не умеет:

- Группировать многотомные архивы в единые сущности
- Извлекать 7z архивы с паролем
- Интерактивно выбирать архивы по номерам с пагинацией
- Понимать концепцию "бэкапа" (архивация → отправка → восстановление)

Нужна функция **backuper**, которая позволяет:
1. Архивировать указанную папку с настраиваемым размером тома и паролем
2. Отправить архивные тома в канал MAX
3. Просмотреть список архивов в канале и скачать выбранные
4. Извлечь архивы с паролем в указанную папку

---

## Constraints

- **7-Zip** должен быть установлен (уже используется в `split_file_with_7z`)
- **MAX канал** — единственный канал связи, браузер должен быть открыт через CDP
- Файлы >49MB разбиваются на тома (лимит CDN MAX)
- Текущий `split_file_with_7z` делает raw split без сжатия — для бэкапа нужно **сжатие + пароль**
- Пароли хранятся в журнале для удобства восстановления
- Архивация директорий — бизнес-логика уровня архиватора, не браузерного слоя

---

## Approach

**Отдельный модуль `backuper.py`** по паттерну `pypi_libs_archiver.py` и `channel_downloader.py` с двумя режимами:

| Режим | Описание |
|-------|----------|
| **Backup** | Архивировать папку → отправить тома в канал |
| **Restore** | Сканировать канал → скачать архивы → извлечь |

**Почему отдельный модуль:**
- Backuper — это upload + download, а downloader только скачивает
- Нужен новый журнал (backup журнал ≠ download журнал)
- Нужна новая логика архивации директорий (сжатие + пароль)
- Двойная ответственность нарушает SRP

**Почему не в `browser_max.py`:**
- `browser_max.py` — браузерный слой, архивация директорий — бизнес-логика
- `split_file_with_7z` там есть как утилита, но создание архивов из директорий — уровень архиватора

## Architecture

### Компоненты

| Компонент | Ответственность |
|-----------|-----------------|
| `backuper.py` | Главный модуль, класс `Backuper(LogMixin)`, CLI меню, оба режима |
| `backuper_journal.py` | Журнал бэкапов и загрузок, хранение паролей |
| `browser_max.py` (расширение) | `archive_directory_to_volumes()` — архивация директории в 7z тома |
| `browser_max.py` (расширение) | `scan_channel_for_archives()` — сканирование и группировка архивов |

### Журнал (backuper_journal.json)

```json
{
  "backups": [
    {
      "id": "backup_001",
      "source_path": "C:/Users/vldkr/Documents",
      "archive_name": "documents_backup",
      "content_hash": "sha256:abc123...",
      "volume_count": 3,
      "encrypted": true,
      "total_size": 123456789,
      "created_at": "2026-06-09T12:00:00",
      "status": "uploaded"
    }
  ],
  "downloads": [
    {
      "archive_name": "documents_backup",

```

**Пароли в открытом виде** — для личного использования это ок. Шифрование паролей — оверинжиниринг.

## Data Flow — Backup (Загрузка)

```
Пользователь выбирает "Backup"
  │
  ├─ 1. Ввод source_path (папка для бэкапа)
  │     └─ валидация: существует? является директорией?
  │
  ├─ 2. Ввод archive_name
  │     └─ дефолт: "{имя_папки}_{дата}"
  │
  ├─ 3. Выбор режима томов:
  │     [1] Однотомный архив
  │     [2] Многотомный (размер из конфига, дефолт 49M)
  │     [3] Многотомный (пользовательский размер)
  │
  ├─ 4. Вопрос про пароль:
  │     [y/N] Использовать пароль?
  │     └─ если да → ввод пароля (скрытый)
  │
  ├─ 5. Проверка дубликатов:
  │     └─ quick hash: список файлов (имя + размер + mtime)
  │     └─ если hash совпадает → "Уже есть бэкап. Переписать?"
  │
  ├─ 6. Архивация:
  │     └─ archive_directory_to_volumes(source, name, volume_size, password)
  │     └─ 7z a -v49m -mx=5 -pPassword output.7z ./source_folder/
  │
  ├─ 7. Отправка в канал:
  │     └─ текст: "Бэкап: {archive_name} | {N} томов | {size}"
  │     └─ BrowserMAX.send_message_with_files(text, volumes)
  │     └─ каждый том отправляется отдельно, подтверждение по filename
  │
  ├─ 8. Cleanup:
  │     └─ удалить тома из temp после отправки
  │
  └─ 9. Журнал:
        └─ записать запись с hash, размером, статусом
```

## Data Flow — Restore (Скачивание)

```
Пользователь выбирает "Restore"
  │
  ├─ 1. Подключение к браузеру, переход в backup канал
  │
  ├─ 2. Сканирование канала:
  │     └─ scan_channel_for_archives()
  │     └─ находит все .7z файлы, группирует тома:
  │         "documents.7z.001" + ".002" + ".003" → один архив
  │         "photos.7z" → один архив (однотомный)
  │
  ├─ 3. Показ списка с пагинацией:
  │     └─ страница 1/3:
  │         #  Имя архива              Томов   Размер     Дата
  │         1  documents_backup         3      145 MB    09.06
  │         2  photos_2026             1       89 MB    08.06
  │     └─ [←] [→] для навигации
  │
  ├─ 4. Выбор действия:
  │     [1] Скачать выбранные (указать номера через запятую)
  │     [2] Скачать все
  │     [3] Выход
  │
  ├─ 5. Ввод папки для сохранения
  │     └─ дефолт из конфига
  │
  ├─ 6. Парольный режим (если есть зашифрованные архивы):
  │     [1] Один пароль на все архивы
  │     [2] Пароль для каждого архива отдельно
  │     └─ проверяет журнал на сохранённые пароли
  │
  ├─ 7. Скачивание:
  │     └─ для каждого архива:
  │       ├─ скачать все тома через requests + cookies
  │       ├─ запросить пароль (если зашифрован и нет в журнале)
  │       ├─ объединить тома (если многотомный)
  │       ├─ извлечь 7z с паролем
  │       └─ удалить тома после извлечения
  │
  └─ 8. Журнал + итог:
        └─ записать скачанные архивы
        └─ показать статистику
```

## Томная группировка при сканировании

При сканировании канала находим файлы с паттерном `.7z` и `.7z.NNN`, группируем по базовому имени:

| Найденный файл | Базовое имя | Группа |
|----------------|-------------|--------|
| `documents.7z.001` | `documents.7z` | documents (3 тома) |
| `documents.7z.002` | `documents.7z` | documents (3 тома) |
| `documents.7z.003` | `documents.7z` | documents (3 тома) |
| `photos.7z` | `photos.7z` | photos (1 том) |
| `code.7z.001` | `code.7z` | code (2 тома) |
| `code.7z.002` | `code.7z` | code (2 тома) |

**Результат для пользователя:**
1. documents (3 тома)
2. photos (1 том)
3. code (2 тома)

## Конфигурация

```yaml
backuper:
  channel_url: ""                    # URL канала для бэкапов (или BACKUP_CHANNEL_URL из .env)
  default_volume_size: "49M"         # Дефолтный размер тома
  compression_level: "5"             # Уровень сжатия 0-9
  output_dir: "./temp_backups"       # Temp папка для архивов
  download_dir: "./restored"         # Дефолтная папка для восстановления
  page_size: 10                      # Архивов на страницу в CLI
```

Добавляем в `.env`:
```env
BACKUP_CHANNEL_URL=https://web.max.ru/...
```

## Error Handling

| Сценарий | Поведение |
|----------|-----------|
| 7z не найден | Сообщение об ошибке, предложение проверить установку |
| Папка пуста | Отказ от архивации с предупреждением |
| Браузер не подключен | Попытка подключения, затем отказ |
| Том не отправлен | Retry (3 попытки), помечаем бэкап как failed |
| Скачивание прервано | Журнал сохраняет прогресс, можно возобновить |
| Неверный пароль | 3 попытки, переход к следующему архиву с пометкой ошибки |
| Частичный бэкап | Удаляем отправленные тома из канала, помечаем как failed |

## Testing Strategy

- **Юнит-тесты** для группировки томов (парсинг имён файлов → группы архивов)
- **Юнит-тесты** для валидации ввода (размер тома, имя архива)
- **Интеграционный тест** архивации пустой папки → ошибка
- **Интеграционный тест** архивации папки с файлами → созданы тома
- **Ручное тестирование** полного цикла: бэкап → сканирование → восстановление → проверка содержимого

## Open Questions

**Решено:**
1. **Хранение паролей** — в открытом виде в JSON. Для личного бэкапера это ок.
2. **Хеширование содержимого** — quick hash: список файлов (имя + размер + mtime), не содержимое.
